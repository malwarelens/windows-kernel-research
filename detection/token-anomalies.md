# 令牌异常：data-only 提权的结果痕迹

> 本条目补上 [`detection/README.md`](README.md) 中计划的占位条目，把
> [win32k 回调滥用观测点](win32k-callback-abuse.md) 第 5 步提到的
> 「无正常授权路径的令牌异常」展开为一份可复用的通用清单。它适用于
> 一类常见的内核提权收尾手法：不执行内核代码，只在内核数据结构层面
> 让某个进程的令牌在事实上变成高权限令牌（概念层面即本仓库各分析中
> 提到的 data-only 提权）。这里只写**结果检测**，不描述令牌的改写方法。
> 除特别注明外，各观测点未在真实 EDR / ETW 环境逐一实测，均为
> 「推测/待验证」，落地前请先在自有环境验证覆盖范围与噪声水平。

## 为什么抓令牌，而不是只抓漏洞触发点

触发点随漏洞而变（win32k 回调、CLFS 元数据解析、驱动 IOCTL……），
但只要利用的目标是本地提权，其结果通常收敛到同一件事：某个原本
低权限的进程或它随后创建的子进程，拿到了与其创建路径不符的令牌。
触发瞬间往往只有 EDR 的内核层遥测才看得见，而结果会在进程创建、
登录会话与服务安装等常规日志里留下可交叉核对的矛盾。结果检测不
依赖具体 CVE，补丁合规数据又能缩小范围，因此更耐用。

## 正常基线：一份令牌应当自洽

一个进程的令牌至少应在以下几项上与其创建路径互相印证：

- **用户与完整性**：令牌用户、完整性级别与登录会话的用户一致；
  普通用户经 UAC 提升时，应能找到对应的提权同意与新登录记录。
- **特权集合**：令牌携带的特权与该账户 / 服务账户的预期相符，
  不会在进程运行中途无故多出一批高权限特权。
- **登录会话可溯源**：令牌的登录 ID 能对应到一次真实的登录事件
  （如安全日志 4624，新登录被赋予特殊特权时另有 4672），而不是
  一个从未出现过的孤儿会话。
- **创建路径可解释**：SYSTEM 进程通常由服务控制管理器、计划任务
  或已有的 SYSTEM 进程创建，并伴随服务安装（安全日志 4697 /
  系统日志 7045）、计划任务注册等记录中的至少一项。

## 观测点清单

| 观测点 | 为什么可疑 | 可能的遥测来源 | 说明 |
|---|---|---|---|
| 已有进程的令牌用户 / 完整性在运行中途突变（如普通用户 → SYSTEM），且同期无新登录、无 UAC 提权、无服务创建记录 | 正常授权路径都会先产生一个新的登录或进程创建事件；原地突变正是 data-only 改写令牌指针的结果形态 | EDR 的令牌周期扫描 / 创建时快照与后续状态比对（覆盖因产品而异） | 强信号，但依赖 EDR 是否保存创建时令牌快照；标准 Windows 日志本身不记录已有进程的令牌变更 |
| 低权限父进程直接创建出 SYSTEM 子进程 | 被提权的进程本身可能没有新日志，其子进程的创建却会被如实记录：父子权限关系与任何已知的提权路径都对不上 | Sysmon Event ID 1（`User` 与 `ParentImage` / 父进程信息并读）；安全日志 4688（需开启进程创建审核） | 本清单在标准工具下最可落地的一条；注意父进程信息要与子进程的 `User` 放在同一条规则里判定 |
| SYSTEM 进程的映像位于用户可写路径（用户目录、临时目录等），且父进程是普通应用 | 合法 SYSTEM 服务与系统组件几乎都从系统目录、由系统路径启动 | Sysmon Event ID 1；EDR 进程遥测 | 与上一条组合时信号更强；开发 / 运维工具是主要误报源，见下 |
| 令牌特权集合与账户预期明显不符（如交互式普通用户进程的令牌带有成批默认禁用的高权限特权并被启用） | 复制 / 借用高权限令牌的结果之一是特权集合一并越界，而不是像正常提权那样只多出目标账户应有的特权 | EDR 令牌检查；需自建账户—特权基线 | 待验证：不同 Windows 版本上 SYSTEM 令牌的默认特权集合并不相同，基线必须按版本与角色在自有环境采集，不要套用网传清单 |
| 令牌登录 ID 无法对应到任何一次登录事件，或对应会话的用户与令牌用户不一致 | 正常令牌都源于一次真实登录；被嫁接的令牌在会话账本上对不平 | 安全日志 4624 / 4672 与 EDR 令牌中的登录 ID 做关联 | 需要集中化日志关联，单机人工排查时价值有限 |
| 同期缺少一切令牌操作痕迹 | 经正常 API 的令牌复制 / 模拟会经过 `OpenProcessToken`、`DuplicateTokenEx`、`SetThreadToken` 等调用；data-only 手法不走 API，痕迹的「缺席」本身是旁证 | EDR 的 API / syscall 遥测（覆盖因产品而异） | 只能作旁证，不能单独告警：未覆盖这些 API 的遥测同样会表现为缺席 |

## Sysmon 与安全日志的能力边界

- **Sysmon 不监控令牌变更**：它在进程创建时记录一次 `User`，
  已有进程的令牌事后被改写不会产生新事件。Sysmon 在本主题下的
  价值是覆盖提权**之后**的动作（SYSTEM 子进程、后续的持久化
  行为），与 [win32k 条目](win32k-callback-abuse.md) 的结论一致。
- **安全日志记的是登录与创建，不是令牌本身**：4624 / 4672 能
  证明「一次高权限登录真实发生过」，4688 能证明「一个进程以
  什么令牌被创建」；两者的用处在于与 EDR 声称的令牌状态做
  交叉核对，矛盾点才是信号。
- **创建时快照决定上限**：基于进程创建回调的遥测同样只看到
  创建那一刻的令牌。若产品没有周期性复查或令牌完整性校验，
  「已有进程原地提权」在原理上就可能全程无日志——这也是本类
  检测必须与补丁合规（目标机器是否缺对应累积更新）联动的原因。

## 误报与排除

以下场景会产生表面相似的 SYSTEM 进程，使用前先按签名、路径、
父进程与变更窗口排除：

- 合法安装器与更新程序经 UAC / 服务路径拉起的 SYSTEM 子进程；
- 管理员使用的远程运维工具（典型如以 SYSTEM 运行的远控 / 部署
  代理）——应有对应的服务安装与运维变更记录；
- 计划任务以 SYSTEM 身份运行用户目录下的脚本（基线应登记这类
  既有任务，而不是一概告警）；
- 备份、安全软件自身的 SYSTEM 工作进程（映像多在厂商安装目录
  且有有效签名）。

## 使用建议

- **按矛盾判定**：单一观测点不定性；「令牌状态与登录 / 创建 /
  服务记录互相矛盾」才是本条目的核心判定式，至少要有一处可
  独立复核的日志矛盾再升级处置。
- **先建基线再上线**：SYSTEM 进程的映像路径、父进程、账户—特权
  对应关系都强依赖环境，先以观察模式采集一至两周再转告警。
- **与补丁合规联动**：同一时间窗内目标机器缺少已知内核提权漏洞
  的累积更新时，提高上述矛盾信号的优先级，并按潜在利用事件
  保留内存与磁盘证据，不要只按普通告警关闭。
