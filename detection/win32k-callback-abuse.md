# win32k 用户模式回调滥用：通用观测点

> 本条目把 [CVE-2021-1732 分析](../analyses/CVE-2021-1732/analysis.md)「检测与
> 缓解」一节与 [win32k 用户模式回调笔记](../kernel-notes/win32k-user-callbacks.md)
> 中分散的观测点抽取为一份可复用的通用清单，适用于「回调期间改对象状态」
> 这一类缺陷（1732 之后的 CVE-2022-21882 据公开分析亦为同一回调、同一
> 转换手法）。这里写的是**观测思路**：除特别注明外，各观测点未在真实
> EDR / ETW 环境逐一实测，落地前请先在自有环境验证覆盖范围与噪声水平。

## 典型行为链

单点行为大多不足以定性，这类利用可识别的是下面这条**组合链**：

1. 普通应用进程在运行时改写自身 `PEB.KernelCallbackTable` 的条目
   （如 `xxxClientAllocWindowClassExtraBytes`），指向非 user32 / win32u
   的私有代码页；
2. 进程频繁创建 / 销毁带 `cbWndExtra > 0` 的窗口，做桌面堆槽位试探；
3. 在窗口**创建过程中**调用 `NtUserConsoleControl`，把正在创建的窗口
   转换成控制台类型——业务软件中极罕见；
4. 随后对该窗口进行 `SetWindowLong` 类操作，写向本不应可达的内核
   桌面堆区域；
5. 若利用成功，后段出现 data-only 提权的结果痕迹：低完整性进程在
   没有正常授权路径（无 UAC 提权、无服务创建、无令牌操作 API 记录）
   的情况下令牌变为 SYSTEM。

## 观测点清单

| 观测点 | 为什么可疑 | 可能的遥测来源 | 说明 |
|---|---|---|---|
| 进程改写自身 `KernelCallbackTable` 条目 | hook 回调是这类利用的标准第一步，正常业务软件极少这样做 | EDR 内存扫描 / 写监控 | 强信号；Sysmon 不覆盖此行为 |
| 窗口创建期间调用 `NtUserConsoleControl` 做类型转换 | 把普通窗口转成控制台类型是字段语义混淆的关键一步 | EDR 的 syscall / ETW 层遥测（如 `Microsoft-Windows-Win32k` provider，具体事件覆盖因产品而异） | `NtUser*` 调用不在 Sysmon 记录范围内 |
| 短时间高频创建 / 销毁窗口并伴随桌面堆槽位复用试探 | 触发需要让目标对象的 `tagWND` 落入预留槽位 | EDR 行为遥测 | 单独出现噪声大，只作组合链的一环 |
| `win32kfull.sys` 相关非预期 bugcheck（桌面堆损坏类）在缺补丁机器上集中出现 | 触发失败 / 打崩同样是利用进行中的痕迹 | 崩溃转储与补丁合规数据 | 应按潜在利用事件排查，不要只归为稳定性问题 |
| 无正常授权路径的令牌异常（进程令牌突变为 SYSTEM） | data-only 提权的最终结果，与具体漏洞点无关 | EDR 令牌监控；Sysmon 可覆盖其后的 SYSTEM 进程创建（Event ID 1）等动作 | 结果检测比触发瞬间检测更可靠 |

## 使用建议

- **按链判定，不按单点告警**：上表任意单点都可能有合理成因（调试器、
  UI 自动化与钩子工具可能出现其中个别行为）；至少两个观测点在同一
  进程、同一时间窗内共现，且目标机器缺少对应月度累积更新时，再升级
  为事件处置。
- **承认 Sysmon 的边界**：Sysmon 对 win32k 回调滥用本身基本不可见，
  它能覆盖的是利用成功**之后**的动作。检测设计应把重心放在
  「结果检测 + 补丁合规」上，而不是指望在触发瞬间告警。
- **减面优先**：对不需要 GUI 的服务 / 沙箱进程启用 win32k 系统调用
  禁用策略（win32k lockdown），可直接切断整条触发链，比任何单点
  检测都干净。
